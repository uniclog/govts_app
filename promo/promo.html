01Слои

Голос, control и чат идут по одному UDP-сокету (по умолчанию :9000). Демонстрация экрана — отдельный тракт: HTTPS-сигнализация (:9002) и WebRTC (UDP 20000–20100).

React UI ── Wails service (internal/ui/wails) ── clientapp (lifecycle, reconnect)
   └─ client (state, jitter, mixer, requests)
       └─ transport/udp.ClientPacketConn ── DatagramCodec (protocol.SecureDatagramCodec)
           ══ UDP ══
       transport/udp.ServerPacketConn ── SecureDatagramCodec
   └─ voice.ServeUDP (один цикл) ── Hub (сессии, каналы, ревизия) ── persist (SQLite)

Граница: VoicePacket — логический пакет; DatagramCodec превращает его в байты провода (шифрует/расшифровывает) с учётом направления и KeyOwnerID.

02Логический пакет VoicePacket

internal/protocol/packet.go. Big-endian.

Type1 B
SessionID8 B, uint64
Sequence4 B, uint32
RequestID4 B, uint32
Payload0..1200 B
ПолеСмысл
TypeТип пакета (см. §3). Неизвестный тип — ошибка декодирования.
SessionIDСессия отправителя. Выдаётся сервером, crypto/rand, ненулевая. 0 — только у auth- и status-пакетов. В пересылаемом голосе — ID говорящего.
SequenceДля голоса — номер кадра (jitter buffer). В auth-пакетах переиспользуется как версия протокола.
RequestIDКорреляция запрос/ответ для control-пакетов; ключ дедупликации в voice.RequestCache. Для голоса 0.
PayloadЗависит от типа. Голос — непрозрачный Opus-кадр; сервер его не декодирует.

Итого 17 B заголовка + до 1200 B payload = до 1217 B открытого пакета.

04Handshake

internal/auth/handshake.go, клиент — internal/client/secure_handshake.go, сервер — internal/voice/auth.go.

Transcript T

T = H("govts-auth-v1" ‖ RequestID ‖ version ‖ AuthInit целиком ‖
      serverEd25519Pub ‖ serverX25519Eph ‖ nonceS)

Обе подписи (сервера и клиента) — Ed25519 над T. Изменение любого поля — в том числе версии и RequestID — ломает проверку. Сервер требует версию клиента не ниже 0.2.5.

Вывод ключей

shared = X25519(eph_priv_own, eph_pub_peer)
c2s ‖ s2c ‖ ack = HKDF-SHA256(ikm = shared, salt = T,
                              info = "govts-udp-v1 traffic and ack"), 3 × 32 B
  • Ключи направлений разные → свои счётчики, пара key+nonce не повторяется.
  • Эфемерные X25519 новые на каждое подключение → forward secrecy для завершённых сессий.
  • Клиент ставит трафиковые ключи только после проверки HMAC в AuthAck.

Состояние незавершённого handshake на сервере

  • Ключ — (IP:port, RequestID), живёт 30 с.
  • Повтор идентичного AuthInit/AuthFinish → тот же challenge/ack (UDP-ретраи безопасны). Тот же RequestID с другими данными → отказ.
  • Лимиты: 60 новых handshake/мин с IP, 512 одновременных pending.
  • Следствие: если NAT поменяет порт во время ретрая, handshake начнётся заново.

TOFU

Клиент хранит %APPDATA%\Sonoryx\voice-pins.json: host:port → serverEd25519Pub. Первый контакт закрепляет ключ, смена ключа — отказ подключения. Идентичность клиента — seed в client.seed (Base64, не зашифрован); учётная запись на сервере = публичный ключ, имя — только отображение.

05Защищённая запись на проводе

internal/protocol/secure.go. Шифруется весь VoicePacket, включая его 17-байтный заголовок.

0xFF1 B
KeyOwnerID8 B
Counter8 B
Ciphertext(VoicePacket)17..1217 B
GCM tag16 B

Фиолетовый — внешний заголовок (открыт, но входит в AAD). Зелёный — шифртекст. Накладные 33 B, максимум на проводе 1250 B.

ЭлементДетали
0xFFМаркер записи. Без него датаграмма разбирается как открытый пакет и принимается только для auth/status/Error(SessionID=0); на сервере ещё Hello (ради ответа «upgrade required»).
KeyOwnerIDСессия, чьим ключом защищена запись. При пересылке S→C — это получатель, а внутренний SessionID — говорящий. Клиент отвергает запись с чужим KeyOwnerID.
Counteruint64, свой на каждое направление, начинается с 1, растёт перед отправкой; при переполнении — ошибка. Nonce GCM = 00000000 ‖ Counter (12 B).
Anti-replayМаксимум принятого счётчика + окно 64. Новый больший — принимается; внутри окна и не виденный — принимается (переупорядочивание UDP); повтор или старше окна — отказ. Окно двигается только после успешного GCM Open и проверки внутреннего пакета.

Проверки после расшифровки

  1. есть security context для KeyOwnerID;
  2. внутренний SessionID соответствует ожидаемой сессии;
  3. auth-пакеты внутри записи запрещены;
  4. адрес клиента (IP:port) совпадает с адресом активной сессии (на сервере);
  5. тип и размер внутреннего пакета допустимы.

Любой отказ → ErrRejectedDatagram: пакет отбрасывается, причина агрегируется в logging.NewFailures, цикл приёма продолжает работу. Ошибки сокета — фатальны.

06Сервер: цикл обработки

internal/voice/server.go — ServeUDP. Один goroutine читает сокет и обрабатывает пакеты последовательно.

ReadPacket (decode + decrypt)
 ├─ rejected            → счётчик причин, continue
 ├─ ServerStatusRequest → лимитер (100/с глобально, 120/мин на IP, ≤4096 IP) → Ack
 ├─ ChatRequest         → chatWorker.enqueue (очередь 128, ≤4 на пользователя)
 └─ остальное, под policyGate (sync.Mutex):
     ├─ Hello           → Error "client upgrade required"
     ├─ AuthInit/Finish → Authenticator.Handle
     ├─ Kick/Ban/Drag   → HandleModeration
     └─ HandlePacket    → Voice, Heartbeat, Disconnect, JoinChannel,
                          Snapshot, MediaCredential, AudioState

Параллельно работают:

  • DispatchEvents — забирает события из outbox Hub (ёмкость 256) и рассылает их.
  • CleanupLoopWithPolicyGate — удаляет сессии без активности 30 с, снимает ключи из codec и RequestCache.
  • chatWorker — SQLite-операции чата вне голосового цикла.
  • HTTPS media-сервер и консоль — берут тот же policyGate.
Узкое место: policyGate берётся и для голосовых пакетов, а AuthFinish делает SQLite-запрос под ним. См. project-review.md §1.1.

Hub

internal/voice/hub.go — источник истины под sync.RWMutex: сессии (ID, адрес, user_id, права, канал, mute/deafen, media credential, время активности), дерево каналов, StateRevision. Каждая мутация увеличивает ревизию и кладёт StateEvent в outbox. Наружу отдаются только копии.

RequestCache

internal/voice/cache.go. Ключ — (SessionID, RequestID). Повтор control-запроса получает сохранённый ответ, мутация не выполняется дважды. Клиент повторяет запрос до ответа или таймаута (internal/client/request.go).

07Голосовой тракт

Отправка (клиент)

malgo capture (PCM) → усиление 0..2 (насыщение int16) → RNNoise (опц.) → VAD/voice gate (опц.: level | vad | hybrid,
pre-roll 60 мс, hangover 300 мс) → Opus encode, кадр 20 мс
→ VoicePacket{Type=Voice, SessionID=own, Sequence=n++} → AES-GCM(c2s) → UDP

Без микрофона клиент остаётся в канале в состоянии mute и продолжает принимать звук.

Усиление микрофона (AudioControlState.MicrophoneGain, applyGain в internal/client/capture.go) применяется в RecordLoop до индикатора, RNNoise и VAD; значение хранится в настройках клиента (microphoneGain, по умолчанию 1).

До подключения раздел настроек «Микрофон» запускает тот же тракт без Opus и отправки (internal/clientapp/preview.go): индикатор показывает, что прошло бы порог, а кнопка прослушивания проигрывает пропущенные гейтом кадры на устройство вывода. При подключении предпросмотр останавливается.

Сервер

  1. Проверка: сессия существует, адрес совпадает (иначе пакет молча отброшен).
  2. Учёт прибытия (RecordVoicePacket) для статистики потерь.
  3. Получатели = все сессии в канале отправителя, кроме него самого (deafen учитывается по событиям/клиенту).
  4. При включённом -voice-redundancy и клиенте ≥ 0.2.13 — VoiceBundle с текущим и предыдущим кадром, иначе обычный Voice (подробно — раздел 08).
  5. На каждого получателя — отдельная запись AES-GCM(s2c получателя), KeyOwnerID = получатель.

Приём (клиент)

receive loop → разделение voice / control
→ jitter buffer на отправителя (глубина 3 кадра, сортировка по Sequence,
  до 3 подряд замаскированных кадров, очистка потока после 30 с тишины)
→ Opus decoder на отправителя (битый кадр отбрасывается, декодер пересоздаётся)
→ громкость/mute конкретного участника (коэффициент 0..9)
→ mixer: очередь ≤ 5 кадров (100 мс) на отправителя, вытеснение старых
→ malgo playback, тик 20 мс

Индивидуальная громкость применяется локально после декодирования: scalePCM умножает PCM-отсчёты на коэффициент 0..9 с округлением и ограничением диапазоном int16; усиление может приводить к клиппингу. Интерфейс показывает условную шкалу 0–300 pt. с шагом 1: коэффициент вычисляется как (level / 100)², поэтому 100 соответствует ×1 (по умолчанию), 200 — ×4, 300 — ×9. При чтении коэффициента положение ползунка восстанавливается как round(sqrt(gain) × 100). Значение передаётся через 40 мс после последнего изменения и сразу при отпускании указателя или клавиши. «Заглушить» задаёт коэффициент 0, «Включить звук» — 1 (100 pt.). Значения хранятся в памяти по SessionID и очищаются при выходе участника или сбросе сессии. Источники: cmd/desktop/frontend/src/features/participants/ParticipantRow.tsx, internal/client/audio_controls.go, internal/client/decode.go, internal/client/live.go, internal/client/state.go.

08Устойчивость к потерям

Голос идёт по UDP без ретрансмиссий: ждать повторную отправку дольше, чем длится кадр (20 мс), бессмысленно. Поэтому потери компенсируются на трёх уровнях. Исходная мотивация — DPI на части маршрутов отбрасывает 10–20 % датаграмм в направлении server → client (readme_docs/fixes/udp-downlink-packet-loss.md).

1. Redundancyсервер повторяет кадр N−1 в датаграмме N
2. Jitter bufferпереупорядочивание, дубли, подтверждение пропуска
3. Opus PLCсинтез до 3 потерянных кадров подряд
4. Обрывдлиннее 60 мс — тишина до следующего кадра

Уровень 1. Server-side redundancy: PacketVoiceBundle

internal/voice/media.go, internal/protocol/voice_bundle.go, Hub.SwapLastVoiceFrame.

Payload VoiceBundle:
u8  version = 1
u8  frame_count = 1..2
repeat frame_count:
    u32 sequence
    u16 payload_length
    u8  opus[payload_length]        // сначала N−1, затем N
  1. Сервер хранит у каждой сессии-отправителя последний кадр {sequence, opus} (копию байтов).
  2. На кадр N: если сохранённый кадр — ровно N−1, собирается bundle [N−1, N]. Дубликат, перестановка или разрыв sequence → bundle не собирается, уходит обычный Voice.
  3. Bundle — это одна датаграмма: оба кадра лежат в payload одного VoicePacket, поэтому на них действует тот же лимит payload 1200 B: 2 + (6 + len(N−1)) + (6 + len(N)) ≤ 1200. При 24 кбит/с кадр ≈ 60 B, bundle ≈ 134 B — запас почти десятикратный. Если лимит всё же превышен (очень высокий bitrate), сервер не делит bundle на части, а отправляет обычный Voice только с кадром N; копия N−1 в этот раз не передаётся (newVoiceBundlePacket → RouteVoicePacket).
  4. Получатели с поддержкой (клиент ≥ 0.2.13, по версии из AuthInit → Session.VoiceBundles) получают bundle, остальные — обычный Voice.
  5. Клиент раскладывает оба кадра в jitter buffer отправителя; уже полученная копия N−1 отбрасывается как дубликат.

Число датаграмм в секунду не растёт (в отличие от двойной отправки, которую DPI с rate limit может прорежать так же), растёт только размер: +~6 B заголовка кадра + Opus-кадр ≈ 60 B при 24 кбит/с.

Выключено по умолчанию. Включается флагом сервера -voice-redundancy (cmd/server/main.go:39). Без него работают только уровни 2–4.

Оценка эффекта

Кадр теряется безвозвратно, только если потеряны и его датаграмма, и следующая (с копией). При независимых потерях с вероятностью p:

Потери датаграмм pБез redundancyС redundancy (p²)Из них скроет PLC
5 %5 %0,25 %почти все
10 %10 %1 %одиночные и пары
20 %20 %4 %серии ≤ 3 кадров

При пакетных (burst) потерях результат хуже p²: серия из двух и более подряд потерянных датаграмм восстанавливается лишь частично. Цена — до +20 мс эффективной задержки на ожидание копии, она укладывается в окно jitter buffer (3 кадра ≈ 60 мс).

Уровень 2. Jitter buffer

internal/client/jitter.go, отдельный экземпляр на каждый SenderID, DefaultJitterDepth = 3.

  • Старт: воспроизведение начинается, когда накоплено 3 кадра (или по таймеру тиков).
  • Переупорядочивание: кадры хранятся в map по Sequence и выдаются строго по порядку; сравнение через int32(a−b) < 0 корректно при переполнении uint32.
  • Дубликаты (в том числе копии из bundle) — счётчик Duplicates, отброс. Опоздавшие (Sequence уже проигран) — TooOld, отброс.
  • Подтверждение потери: пропуск считается потерей, только когда в буфере набралось ≥ depth более поздних кадров либо истекли depth тиков по 20 мс без нужного кадра. Так кадр, ещё способный прийти, не объявляется потерянным раньше времени.
  • При подтверждённом пропуске длиной d: Lost += d, в поток вставляется min(d, 3) заглушек MediaFrame{Missing: true}, курсор переходит к ближайшему имеющемуся кадру.
пришли:   41 42 __ 44 45 46        (43 потерян)
выдано:   41 42 [43 Missing] 44 45 46
пришли:   50 __ __ __ __ __ 56     (пропуск 5)
выдано:   50 [51 M][52 M][53 M] 56  (54–55 не синтезируются: обрыв)

Уровень 3. Opus PLC

internal/client/decode.go, internal/audio/opus.go → OpusDecoder.ConcealLoss() → pion/opus Decoder.DecodePLC.

  • Обычный кадр — Decode(data); Missing — ConcealLoss() того же декодера отправителя: PLC экстраполирует из его внутреннего состояния, а следующий настоящий кадр декодируется с сохранённым контекстом.
  • PLC-кадр идёт дальше как обычный PCM-кадр с исходными SenderID/Sequence/Duration — микшер получает ровно один кадр на каждые 20 мс, шкала времени не сжимается.
  • Если у отправителя ещё нет декодера (потеря до первого кадра) — заглушка пропускается (errLossNotConcealed).
  • Битый Opus-кадр не роняет поток: кадр отбрасывается, декодер этого отправителя пересоздаётся.

Уровень 4. Длинный разрыв

maxConcealedFrames = 3: дольше 60 мс речь не синтезируется — это давало бы «булькающий» звук. Остаток пропуска — тишина до следующего настоящего кадра. Потерю последнего кадра перед паузой обнаружить нельзя (нет следующего Sequence), и это допустимо: voice gate отправляет hangover 300 мс, хвост реплики не обрезается.

Ограничение задержки при перегрузе

  • Очередь микшера ≤ 5 кадров (100 мс) на отправителя; при переполнении вытесняется самый старый кадр — задержка не накапливается после всплеска.
  • Поток отправителя без кадров 30 с удаляется вместе с его jitter buffer и декодером.

Измерение потерь

НаправлениеКак измеряется
client → serverСервер ведёт окно прибытия Sequence за 35 с (≤ 4096 записей, дубли не считаются). Heartbeat клиента несёт в Sequence: младшие 14 бит — сколько кадров отправлено за ~30 с, старшие — последний Sequence (16 бит). Сервер отвечает в HeartbeatAck.Sequence долей потерь в сотых процента (0–10000).
server → clientСчётчики jitter buffer клиента: Lost, Concealed, Duplicates, TooOld и гистограмма длин пропусков (onGap).

Обе стороны отображаются в окне статистики «Подключено» (internal/client/connection_stats.go, ConnectionStatsPopup.tsx).

Чего нет

  • Opus in-band FEC (LBRR) и DTX не используются; redundancy реализована на уровне протокола.
  • Глубина jitter buffer фиксированная (3), адаптации под измеренный jitter нет.
  • Направление client → server не защищено redundancy: потерянный на uplink кадр теряется для всех получателей и маскируется только их PLC.
  • Redundancy только для голоса; control-пакеты защищены повторами по RequestID, события — пересинхронизацией по ревизии.

09Синхронизация состояния

  1. После AuthAck клиент запрашивает snapshot: постраничный (internal/protocol/snapshot.go, каждая страница ≤ 1200 B) — сервер, каналы, участники, потоки экрана, ревизия. Snapshot v6 содержит user_id.
  2. Клиент атомарно заменяет своё состояние (client.State), UI получает глубокую копию ClientViewState.
  3. Далее StateEvent (join/move/leave, audio state, экраны, права), каждое с ревизией. Применяется, только если ревизия = текущая + 1.
  4. Разрыв ревизий или ошибка применения → requestResync → новый snapshot.
  5. События best effort. Потерю последнего события ловит проверка ревизии каждые 5 с (метаданные в heartbeat/опросе).
  6. Generation-счётчик клиента отсекает ответы и события от предыдущей сессии после reconnect.

10Жизненный цикл сессии

ФазаЧто происходит
ConnectHandshake → AuthAck → snapshot → JoinChannel в канал с "default": true (или первый неограниченный).
РаботаHeartbeat 5 с; нет ACK за 3 с — признак потери связи. Любой валидный пакет обновляет активность сессии на сервере.
Потеря связиclientapp/reconnect.go: backoff 1 → 2 → 4 → 4… с; каждый раз новый handshake и новая сессия; повторный вход в default-канал.
ЗаменаНовая аутентификация того же аккаунта/endpoint заменяет старую сессию: её ключи и кэш удаляются.

DisconnectЯвный пакет Disconnect → немедленное удаление.
Kick/BanСессия удаляется; бан помечает аккаунт в SQLite и проверяется при каждом AuthFinish.

11Чат

  • Адресат: текущий канал или личный диалог с user_id (в том числе офлайн).
  • Операции ChatRequest: send, history (курсор, вперёд/назад), dialogs, read-позиция. Текст ≤ 1000 B UTF-8, страница ≤ 1200 B.
  • Сервер: очередь 128, ≤ 4 ожидающих на пользователя, таймаут 3 с. Права проверяются под policyGate, SQLite — вне голосового цикла.
  • Идемпотентность: уникальная пара (sender_id, client_id) — повтор после reconnect не создаёт дубль.
  • ChatChanged — уведомление «есть новое»; клиент дополнительно опрашивает раз в 5 с для восстановления потерь.

12Демонстрация экрана

Клиент ── MediaCredentialRequest (UDP, защищённо) ──► Hub выдаёт 32 B credential
Клиент ── HTTPS POST /media/publish|subscribe|stop|unsubscribe ──► media.HTTPHandler
          Headers: X-Govts-Session: <id>, Authorization: Bearer base64url(credential)
          Body: JSON (mediasignal), ≤ 256 KiB, неизвестные поля запрещены
media.Manager (Pion SFU) ── SDP answer ──► клиент
WebRTC DTLS-SRTP, VP8 (+ опциональное аудио), UDP 20000–20100
  • TLS-сертификат самоподписанный (sonoryx-media.crt/.key); клиент сверяет SHA-256 отпечаток — отдельный TOFU, хранится в clientsettings.
  • Доступ к потоку проверяется по состоянию Hub (тот же канал, права); раз в секунду идёт сверка подписок.
  • Публичный адрес ICE задаётся -media-advertised-ip; TURN/TCP fallback нет.

14Что протокол не делает

  • Не E2E: сервер расшифровывает и видит голос и control.
  • Не скрывает: IP/порты, размеры и тайминг пакетов, KeyOwnerID и Counter, имя/ключи/версию в handshake.
  • Нет rekey внутри долгой сессии — новые ключи только при новом handshake.
  • Нет защиты первого TOFU-контакта от активного MITM и нет процедуры ротации ключа сервера.
  • Нет adaptive jitter и Opus FEC/DTX; потери компенсируют VoiceBundle (если включён) и PLC — см. раздел 08.
  • Собственная криптосхема (не TLS/Noise), внешнего аудита и fuzz-тестов wire format нет.
  • Открытая регистрация: любой новый ключ создаёт аккаунт.

01Слои

Голос, control и чат идут по одному UDP-сокету (по умолчанию :9000). Демонстрация экрана — отдельный тракт: HTTPS-сигнализация (:9002) и WebRTC (UDP 20000–20100).

React UI ── Wails service (internal/ui/wails) ── clientapp (lifecycle, reconnect)
   └─ client (state, jitter, mixer, requests)
       └─ transport/udp.ClientPacketConn ── DatagramCodec (protocol.SecureDatagramCodec)
           ══ UDP ══
       transport/udp.ServerPacketConn ── SecureDatagramCodec
   └─ voice.ServeUDP (один цикл) ── Hub (сессии, каналы, ревизия) ── persist (SQLite)

Граница: VoicePacket — логический пакет; DatagramCodec превращает его в байты провода (шифрует/расшифровывает) с учётом направления и KeyOwnerID.

Desktop backend и CLI сборки используют Wails v3.0.0-beta.30: версия закреплена в go.mod, package.json, Taskfile.yml и командах dev-режима build/config.yml; контрольные суммы Go-модуля хранятся в go.sum. Задача version:prepare создаёт build/config.generated.yml из этого шаблона перед запуском dev-режима.

02Логический пакет VoicePacket

internal/protocol/packet.go. Big-endian.

Type1 B
SessionID8 B, uint64
Sequence4 B, uint32
RequestID4 B, uint32
Payload0..1200 B
ПолеСмысл
TypeТип пакета (см. §3). Неизвестный тип — ошибка декодирования.
SessionIDСессия отправителя. Выдаётся сервером, crypto/rand, ненулевая. 0 — только у auth- и status-пакетов. В пересылаемом голосе — ID говорящего.
SequenceДля голоса — номер кадра (jitter buffer). В auth-пакетах переиспользуется как версия протокола.
RequestIDКорреляция запрос/ответ для control-пакетов; ключ дедупликации в voice.RequestCache. Для голоса 0.
PayloadЗависит от типа. Голос — непрозрачный Opus-кадр; сервер его не декодирует.

Итого 17 B заголовка + до 1200 B payload = до 1217 B открытого пакета.

Ступень и счётчик обнуляются, только когда этот срок достигнут. Серия из 2 вызовов без открытой блокировки гаснет через 10 с; один вызов — через 2 мин тишины. Отказ: attention-locked:<секунды>. Клиент ту же лестницу и те же сроки затухания серии держит у себя (features/participants/wakeLimit.ts) и во время паузы пакет не отправляет.

Payload Privileges: join_level u16 ‖ privileges u8; тот же байт идёт в AuthAck под HMAC. Биты: 0 kick, 1 ban, 2 drag, 3 admin, 4 owner (owner только на проводе, из users.owner). Удаление (Hub.DeleteChannel, persist.DeleteChannelBy): канал по умолчанию и канал с подканалами не удаляются; участники переносятся в канал по умолчанию (у каждого останавливается трансляция экрана, событие ParticipantMoved), затем идёт ChannelDeleted; в той же транзакции SQLite удаляются история чата канала и отметки прочтения (chat_messages ссылается на channels внешним ключом). 10 delete-account (сервер ≥ 0.3.7; target — ID аккаунта, нужно право ban, если не владелец; иерархия как у прочих изменений аккаунта; владелец и забаненный аккаунт не удаляются — удаление сняло бы бан). persist.DeleteAccountBy (схема SQLite 6, столбец users.deleted) не стирает строку: сообщения в каналах ссылаются на неё внешним ключом и показывают сохранённое имя отправителя. Ключ заменяется 32 случайными байтами, уровень и права обнуляются, удаляются личные сообщения в обе стороны, диалоги и отметки прочтения; сессии аккаунта отключаются (Hub.RemoveUserSessions). Скрытая запись не видна в списке, не принимает изменений и личных сообщений. Ключ клиента не перевыпускается: при следующем входе FindOrCreateAccount регистрирует по тому же ключу новый аккаунт с уровнем 0 и без прав. После reason операции 7 и 8 несут parent u64 ‖ position u32 ‖ max_users u32 ‖ min_join_level u16 ‖ bitrate u32 ‖ application u8 ‖ name str16 ‖ topic str16 ‖ description str16 (≤ 64 / 128 / 512 B); частота 48 кГц, моно, 20 мс и кодек Opus фиксированы клиентским трактом. Update заменяет все настройки сразу, в том числе родителя и позицию — так канал и перемещается; новый родитель не может быть самим каналом или его потомком, глубина поддерева ≤ 8, имя уникально среди соседей без учёта регистра, канал по умолчанию остаётся без лимита и порога, каналов ≤ 4096 (voice.MaxChannels, channel_admin.go). Поднятый порог отключает участников канала ниже него, уменьшенный лимит текущих не трогает. Клиент двигает канал на одно место стрелками: переставляет соседей и шлёт update для каждого, чья позиция сменилась (позиции становятся 0, 1, 2…; reorderPositions, features/admin/adminRules.ts). Ack: version ‖ op ‖ n_accounts u8 ‖ n_audit u8 ‖ next u64 + записи; страница набирается, пока помещается в 1200 B, next=0 — конец. Для операций 7, 8 и 9 next — ID канала, для 10 — ID аккаунта. Клиент показывает создание, перемещение и удаление только при версии сервера из snapshot ≥ 0.3.7; на старом сервере остаётся правка порога. Аккаунт: id, первые 8 B SHA-256 ключа, join_level, privileges, флаги banned/owner/online, имя ≤ 64 B, причина бана ≤ 128 B. Запись журнала: id, время мс, target, actor ≤ 32 B, action ≤ 32 B, detail ≤ 160 B (сервер укорачивает по границе rune). Иерархия (voice.Administration): локальная консоль меняет любой аккаунт (бан владельца запрещён в SQLite). Удалённо никто не меняет владельца и свой аккаунт. Админ, который не владелец, кроме того не меняет других администраторов и аккаунты с уровнем выше своего, не выдаёт admin и права, которых нет у него, не ставит уровень аккаунта или канала выше своего. Каждая мутация пишет audit с actor=user_id в той же транзакции. Ответы кэшируются в RequestCache; новых запросов ≤ 30 за 10 с на сессию. Источники: internal/protocol/admin.go, internal/voice/admin.go, admin_packet.go, клиент internal/client/admin.go, UI features/admin/AdminPanel.tsx.

04Handshake

internal/auth/handshake.go, клиент — internal/client/secure_handshake.go, сервер — internal/voice/auth.go.

Transcript T

T = H("govts-auth-v1" ‖ RequestID ‖ version ‖ AuthInit целиком ‖
      serverEd25519Pub ‖ serverX25519Eph ‖ nonceS)

Подписи с разными метками домена: сервер — Ed25519("govts-server-auth-v1" ‖ T), клиент — Ed25519("govts-client-auth-v1" ‖ T) (internal/auth/handshake.go), поэтому подпись одной стороны нельзя выдать за подпись другой. Изменение любого поля — в том числе версии и RequestID — ломает проверку. В Sequence клиент передаёт минимальную версию сервера из version/release.json (сейчас 0.3.0; internal/client/request.go, internal/client/secure_handshake.go). Если версия сервера ниже, он отвечает ServerVersionTooOld (internal/voice/auth.go, internal/voice/control.go). Отдельно сервер отвергает клиента, который запрашивает уровень ниже 0.3.0 (snapshot v7 и presence; minimumSecureClientVersion в internal/voice/auth.go).

Вывод ключей

shared = X25519(eph_priv_own, eph_pub_peer)
c2s ‖ s2c ‖ ack = HKDF-SHA256(ikm = shared, salt = T,
                              info = "govts-udp-v1 traffic and ack"), 3 × 32 B
  • Ключи направлений разные → свои счётчики, пара key+nonce не повторяется.
  • Эфемерные X25519 новые на каждое подключение → forward secrecy для завершённых сессий.
  • Клиент ставит трафиковые ключи только после проверки HMAC в AuthAck.

Состояние незавершённого handshake на сервере

  • Ключ — (IP:port, RequestID), живёт 30 с.
  • Повтор идентичного AuthInit/AuthFinish → тот же challenge/ack (UDP-ретраи безопасны). Тот же RequestID с другими данными → отказ.
  • Лимиты считаются по сети клиента: /24 для IPv4, /64 для IPv6 (addressNetwork). На сеть — 60 новых AuthInit/мин, ≤ 32 pending, 180 AuthFinish/мин и 10 новых аккаунтов/ч (новым считается ключ, которого нет в users, Store.AccountExists). Глобально ≤ 512 pending; при переполнении вытесняется самый старый.
  • Неверная подпись в AuthFinish удаляет challenge: следующий Finish получает «authentication challenge expired», новая попытка — только через новый AuthInit. Ed25519-проверка на один challenge выполняется не чаще одного раза.
  • Ошибки хранилища и установки ключей клиенту приходят как «authentication failed: server error», подробности — в лог сервера.
  • Следствие: если NAT поменяет порт во время ретрая, handshake начнётся заново.

TOFU

Клиент хранит %APPDATA%\Sonoryx\voice-pins.json: host:port → serverEd25519Pub. Первый контакт закрепляет ключ, смена ключа — отказ подключения. Идентичность клиента — seed в client.seed (Base64, не зашифрован); учётная запись на сервере = публичный ключ, имя — только отображение. Имя проходит NFKC-нормализацию и не может содержать управляющие символы и символы формата Unicode (Cf: bidi-override, ZWSP/ZWJ/ZWNJ, BOM); запрет Cf действует и для имён каналов и сервера. Два онлайн-аккаунта не могут занимать одно имя без учёта регистра — AuthFinish получает «display name is already in use». У забаненного аккаунта имя при входе не обновляется (internal/voice/hub.go, internal/persist/store.go).

05Защищённая запись на проводе

internal/protocol/secure.go. Шифруется весь VoicePacket, включая его 17-байтный заголовок.

0xFF1 B
KeyOwnerID8 B
Counter8 B
Ciphertext(VoicePacket)17..1217 B
GCM tag16 B

Фиолетовый — внешний заголовок (открыт, но входит в AAD). Зелёный — шифртекст. Накладные 33 B, максимум на проводе 1250 B.

ЭлементДетали
0xFFМаркер записи. Без него датаграмма разбирается как открытый пакет и принимается только для auth/status/Error(SessionID=0); на сервере ещё Hello (ради ответа «upgrade required»).
KeyOwnerIDСессия, чьим ключом защищена запись. При пересылке S→C — это получатель, а внутренний SessionID — говорящий. Клиент отвергает запись с чужим KeyOwnerID.
Counteruint64, свой на каждое направление, начинается с 1, растёт перед отправкой; при переполнении — ошибка. Nonce GCM = 00000000 ‖ Counter (12 B).
Anti-replayМаксимум принятого счётчика + окно 64. Новый больший — принимается; внутри окна и не виденный — принимается (переупорядочивание UDP); повтор или старше окна — отказ. Окно двигается только после успешного GCM Open и проверки внутреннего пакета.

Проверки после расшифровки

  1. есть security context для KeyOwnerID;
  2. внутренний SessionID соответствует ожидаемой сессии;
  3. auth-пакеты внутри записи запрещены;
  4. адрес клиента (IP:port) совпадает с адресом активной сессии (на сервере);
  5. тип и размер внутреннего пакета допустимы.

Любой отказ → ErrRejectedDatagram: пакет отбрасывается, причина агрегируется в logging.NewFailures, цикл приёма продолжает работу. Ошибки сокета — фатальны.

06Сервер: цикл обработки

internal/voice/server.go — ServeUDP. Один goroutine читает сокет и обрабатывает пакеты последовательно. Authenticator обязателен: без него ServeUDP не запускается.

ReadPacket (decode + decrypt)
 ├─ rejected            → счётчик причин, continue
 ├─ ServerStatusRequest → лимитер (100/с глобально, 120/мин на IP, ≤4096 IP) → Ack
 ├─ ChatRequest         → chatWorker.enqueue (очередь 128, ≤4 на пользователя)
 └─ остальное, под policyGate (sync.Mutex):
     ├─ Hello           → Error "client upgrade required"
     ├─ AuthInit/Finish → Authenticator.Handle
     ├─ Kick/Ban/Drag   → HandleModeration
     ├─ AdminRequest    → HandleAdmin → Administration (SQLite + Hub)
     └─ HandlePacket    → Voice, Heartbeat, Disconnect, JoinChannel,
                          Snapshot, MediaCredential, AudioState,
                          Presence, Attention

Параллельно работают:

  • DispatchEvents — забирает события из outbox Hub (ёмкость 256) и рассылает их.
  • CleanupLoopWithPolicyGate — удаляет сессии без активности 30 с, снимает ключи из codec и RequestCache.
  • chatWorker — SQLite-операции чата вне голосового цикла.
  • HTTPS media-сервер и консоль — берут тот же policyGate.
Узкое место: policyGate берётся и для голосовых пакетов, а AuthFinish делает SQLite-запрос под ним. См. project-review.md §1.1.

Hub

internal/voice/hub.go — источник истины под sync.RWMutex: сессии (ID, адрес, user_id, права, канал, mute/deafen, away, media credential, время активности), дерево каналов, StateRevision. Каждая мутация увеличивает ревизию и кладёт StateEvent в outbox. Наружу отдаются только копии. Новая сессия отклоняется, если онлайн уже -max-sessions сессий (по умолчанию 1000) или у аккаунта их 4 (MaxSessionsPerAccount); сессии того же endpoint, которые заменяются, не учитываются. Media credential сравнивается за постоянное время (subtle.ConstantTimeCompare). AcceptAttention пропускает 2 вызова серии и резервирует слот в том же захвате мьютекса. ReleaseAttention возвращает слот, если кадр цели не отправлен. Отказ пишет блокировку 10 с–10 мин и не снимает её следующим запросом. Обнуление ступени — только по истечении срока.

RequestCache

internal/voice/cache.go. Ключ — (SessionID, RequestID). Повтор control-запроса получает сохранённый ответ, мутация не выполняется дважды. Клиент повторяет запрос до ответа или таймаута (internal/client/request.go).

07Голосовой тракт

Отправка (клиент)

malgo capture (PCM) → усиление 0..2 (насыщение int16) → RNNoise (опц.) → VAD/voice gate (опц.: level | vad | hybrid,
pre-roll 60 мс, hangover 300 мс) → Opus encode, кадр 20 мс
→ VoicePacket{Type=Voice, SessionID=own, Sequence=n++} → AES-GCM(c2s) → UDP

Без микрофона клиент остаётся в канале в состоянии mute и продолжает принимать звук.

Усиление микрофона (AudioControlState.MicrophoneGain, applyGain в internal/client/capture.go) применяется в RecordLoop до индикатора, RNNoise и VAD; значение хранится в настройках клиента (microphoneGain, по умолчанию 1).

До подключения раздел настроек «Микрофон» запускает тот же тракт без Opus и отправки (internal/clientapp/preview.go): индикатор показывает, что прошло бы порог. При подключении предпросмотр останавливается, и индикатор питает тракт сессии. Кнопка прослушивания (AudioControlState.SetMonitor) работает в обоих случаях: EncodeLoopWithPipeline отдаёт пропущенные гейтом кадры в отдельный поток вывода вместо Opus, поэтому в сессии голосовые пакеты не отправляются. Прослушивание выключается при выходе из раздела «Микрофон» и при новом подключении.

Сервер

  1. Проверка: сессия существует, адрес совпадает (иначе пакет молча отброшен).
  2. Проверка скачка Sequence (Hub.AcceptVoiceSequence): вперёд допускается не больше 64 кадров плюс один кадр на каждые 10 мс с предыдущего принятого пакета; дальше пакет молча отбрасывается. Настоящая потеря оставляет паузу и проходит, поддельный скачок — нет. Шаг назад больше 64 считается перезапуском отправителя и сбрасывает точку отсчёта.
  3. Учёт прибытия (RecordVoicePacket) для статистики потерь.
  4. Получатели = все сессии в канале отправителя, кроме него самого (deafen учитывается по событиям/клиенту).
  5. При включённом -voice-redundancy и клиенте ≥ 0.2.13 — VoiceBundle с текущим и предыдущим кадром, иначе обычный Voice (подробно — раздел 08).
  6. На каждого получателя — отдельная запись AES-GCM(s2c получателя), KeyOwnerID = получатель.

Приём (клиент)

Громкость и пак — локальные (идентификаторы паков и кнопочных сигналов — clientsettings). Кнопочные сигналы (микрофон, динамик, «отошёл», «на месте», отправка, свой экран, смена своего канала) можно выключить по одному; отсутствующий id в soundCues значит «включён». «Отошёл» по настройке глушит микрофон и, отдельно, динамик; «на месте» возвращает только то, что выключило само это действие. «Отошёл» и «на месте» выполняются по очереди (clientapp.App.presenceMu); если сервер не подтвердил «на месте», динамик снова глушится. Сигнал «отошёл» и «выключить динамик» доигрываются до того, как deafen очистит буфер; клики по микрофону и динамику обрабатываются по очереди. Переключение читает состояние под тем же замком, что и кнопки (toggleMuted, toggleDeafened, ToggleAway); повторный запрос уже установленного «отошёл» сигнал второй раз не играет. Сигналы те же, что у кнопок. Индикатор входящего звука (activePCM, State.ObserveSpeaking в internal/client/audio_controls.go, вызов в internal/client/decode.go) включается при любом ненулевом отсчёте декодированного PCM, без порога RMS: тихая речь и фоновый шум показывают своего отправителя. Проверка выполняется до индивидуального усиления и проверки deafen, поэтому источник виден даже при локальной громкости 0. Полностью нулевой или пустой кадр не активирует индикатор; после последнего ненулевого кадра он удерживается 300 мс и снимается циклом SpeakingLoop с тиком 50 мс. Индивидуальная громкость применяется локально после декодирования: scalePCM умножает PCM-отсчёты на коэффициент 0..9 с округлением и ограничением диапазоном int16; усиление может приводить к клиппингу. Интерфейс показывает условную шкалу 0–300 pt. с шагом 1: коэффициент вычисляется как (level / 100)², поэтому 100 соответствует ×1 (по умолчанию), 200 — ×4, 300 — ×9. При чтении коэффициента положение ползунка восстанавливается как round(sqrt(gain) × 100). Значение передаётся через 40 мс после последнего изменения и сразу при отпускании указателя или клавиши. «Заглушить» задаёт коэффициент 0, «Включить звук» — 1 (100 pt.). Значения хранятся в памяти по SessionID и очищаются при выходе участника или сбросе сессии. 08Устойчивость к потерям

Голос идёт по UDP без ретрансмиссий: ждать повторную отправку дольше, чем длится кадр (20 мс), бессмысленно. Поэтому потери компенсируются на трёх уровнях. Исходная мотивация — DPI на части маршрутов отбрасывает 10–20 % датаграмм в направлении server → client (readme_docs/fixes/udp-downlink-packet-loss.md).

1. Redundancyсервер повторяет кадр N−1 в датаграмме N
2. Jitter bufferпереупорядочивание, дубли, подтверждение пропуска
3. Opus PLCсинтез до 3 потерянных кадров подряд
4. Обрывдлиннее 60 мс — тишина до следующего кадра

Уровень 1. Server-side redundancy: PacketVoiceBundle

internal/voice/media.go, internal/protocol/voice_bundle.go, Hub.SwapLastVoiceFrame.

Payload VoiceBundle:
u8  version = 1
u8  frame_count = 1..2
repeat frame_count:
    u32 sequence
    u16 payload_length
    u8  opus[payload_length]        // сначала N−1, затем N
  1. Сервер хранит у каждой сессии-отправителя последний кадр {sequence, opus} (копию байтов).
  2. На кадр N: если сохранённый кадр — ровно N−1, собирается bundle [N−1, N]. Дубликат, перестановка или разрыв sequence → bundle не собирается, уходит обычный Voice.
  3. Bundle — это одна датаграмма: оба кадра лежат в payload одного VoicePacket, поэтому на них действует тот же лимит payload 1200 B: 2 + (6 + len(N−1)) + (6 + len(N)) ≤ 1200. При 24 кбит/с кадр ≈ 60 B, bundle ≈ 134 B — запас почти десятикратный. Если лимит всё же превышен (очень высокий bitrate), сервер не делит bundle на части, а отправляет обычный Voice только с кадром N; копия N−1 в этот раз не передаётся (newVoiceBundlePacket → RouteVoicePacket).
  4. Получатели с поддержкой (клиент ≥ 0.2.13, по версии из AuthInit → Session.VoiceBundles) получают bundle, остальные — обычный Voice.
  5. Клиент раскладывает оба кадра в jitter buffer отправителя; уже полученная копия N−1 отбрасывается как дубликат.

Число датаграмм в секунду не растёт (в отличие от двойной отправки, которую DPI с rate limit может прорежать так же), растёт только размер: +~6 B заголовка кадра + Opus-кадр ≈ 60 B при 24 кбит/с.

Выключено по умолчанию. Включается флагом сервера -voice-redundancy (cmd/server/main.go:39). Без него работают только уровни 2–4.

Оценка эффекта

Кадр теряется безвозвратно, только если потеряны и его датаграмма, и следующая (с копией). При независимых потерях с вероятностью p:

При пакетных (burst) потерях результат хуже p²: серия из двух и более подряд потерянных датаграмм восстанавливается лишь частично. Цена — до +20 мс эффективной задержки на ожидание копии, она укладывается в окно jitter buffer (3 кадра ≈ 60 мс).

Уровень 2. Jitter buffer

internal/client/jitter.go, отдельный экземпляр на каждый SenderID, DefaultJitterDepth = 3.

  • Старт: воспроизведение начинается, когда накоплено 3 кадра (или по таймеру тиков).
  • Переупорядочивание: кадры хранятся в map по Sequence и выдаются строго по порядку; сравнение через int32(a−b) < 0 корректно при переполнении uint32.
  • Дубликаты (в том числе копии из bundle) — счётчик Duplicates, отброс. Опоздавшие (Sequence уже проигран) — TooOld, отброс.
  • Подтверждение потери: пропуск считается потерей, только когда в буфере набралось ≥ depth более поздних кадров либо истекли depth тиков по 20 мс без нужного кадра. Так кадр, ещё способный прийти, не объявляется потерянным раньше времени.
  • При подтверждённом пропуске длиной d: Lost += d, в поток вставляется min(d, 3) заглушек MediaFrame{Missing: true}, курсор переходит к ближайшему имеющемуся кадру.

Уровень 3. Opus PLC

internal/client/decode.go, internal/audio/opus.go → OpusDecoder.ConcealLoss() → pion/opus Decoder.DecodePLC.

  • Обычный кадр — Decode(data); Missing — ConcealLoss() того же декодера отправителя: PLC экстраполирует из его внутреннего состояния, а следующий настоящий кадр декодируется с сохранённым контекстом.
  • PLC-кадр идёт дальше как обычный PCM-кадр с исходными SenderID/Sequence/Duration — микшер получает ровно один кадр на каждые 20 мс, шкала времени не сжимается.
  • Если у отправителя ещё нет декодера (потеря до первого кадра) — заглушка пропускается (errLossNotConcealed).
  • Битый Opus-кадр не роняет поток: кадр отбрасывается, декодер этого отправителя пересоздаётся.

Уровень 4. Длинный разрыв

maxConcealedFrames = 3: дольше 60 мс речь не синтезируется — это давало бы «булькающий» звук. Остаток пропуска — тишина до следующего настоящего кадра. Потерю последнего кадра перед паузой обнаружить нельзя (нет следующего Sequence), и это допустимо: voice gate отправляет hangover 300 мс, хвост реплики не обрезается.

Ограничение задержки при перегрузе

  • Очередь микшера ≤ 5 кадров (100 мс) на отправителя; при переполнении вытесняется самый старый кадр — задержка не накапливается после всплеска.
  • Поток отправителя без кадров 30 с удаляется вместе с его jitter buffer и декодером.

Чего нет

  • Opus in-band FEC (LBRR) и DTX не используются; redundancy реализована на уровне протокола.
  • Глубина jitter buffer фиксированная (3), адаптации под измеренный jitter нет.
  • Направление client → server не защищено redundancy: потерянный на uplink кадр теряется для всех получателей и маскируется только их PLC.
  • Redundancy только для голоса; control-пакеты защищены повторами по RequestID, события — пересинхронизацией по ревизии.

09Синхронизация состояния

  1. После AuthAck клиент запрашивает snapshot: постраничный (internal/protocol/snapshot.go, каждая страница ≤ 1200 B) — сервер, каналы, участники, потоки экрана, ревизия. Snapshot v7: у участника в байте флагов кроме mute/deafen есть бит away (1<<2). Пакет AudioState этот бит не несёт.
  2. Клиент атомарно заменяет своё состояние (client.State), UI получает глубокую копию ClientViewState.
  3. Далее StateEvent v2 (join/move/leave, audio state, экраны, ParticipantPresence, ChannelUpdated), каждое с ревизией. Применяется, только если ревизия = текущая + 1. Presence — SessionID и 1 байт 0/1. ChannelUpdated (kind 8, сервер ≥ 0.3.7) несёт канал целиком в формате элемента snapshot (appendChannel): после создания, правки, перемещения и смены порога (Hub.AddChannel, UpdateChannel, SetChannelJoinLevel). Клиент заменяет канал по ID или добавляет его и снова сортирует список по parent, position, ID (sortSnapshotChannels, client/live.go); цикл или лишняя глубина в результате ведут к ресинку. ChannelDeleted (kind 9, сервер ≥ 0.3.7) — channel_id u64; участники к этому моменту уже перенесены событиями ParticipantMoved, клиент убирает канал из списка, а неизвестный ID или оставшийся в канале участник ведут к ресинку. Клиенты до 0.5.9 эти kind не знают, ошибка декодирования ведёт их к ресинку snapshot — новое дерево они получают так же. Смена битрейта или режима Opus своего канала перенастраивает кодер на лету (audio_profile, clientapp/session.go). Свой сигнал «отошёл» / «на месте» клиент ставит в микшер сразу по нажатию (clientapp.SetAway), не дожидаясь ack. Начало трансляции играет всем в канале, включая автора. Свой конец играет clientapp.StopScreen до сетевого запроса; чужой конец — из события. Свой переход играет тот, кто первым сообщит о новом канале: JoinChannelAck, событие ParticipantMoved или snapshot; остальные видят канал уже выставленным и молчат (queueChannelChangeLocked, client/live.go). Ack часто обгоняет событие, а при быстрых переходах или чужом событии посередине ревизия ack прыгает на +2 — клиент уходит в ресинк, и события из этого промежутка отбрасываются. Поэтому snapshot той же сессии сравнивается с прошлым, даже устаревшим после разрыва ревизий (ReplaceSnapshotForGeneration, client/state.go): появившийся или исчезнувший поток играет начало / конец трансляции, а если свой канал не менялся — вход, выход и смена away у его участников, каждый вид не больше одного раза (queueParticipantDiffLocked). После своего перехода участники нового канала не озвучиваются. Первый snapshot сессии, повтор без изменения и свой конец трансляции из snapshot молчат.
  4. Разрыв ревизий или ошибка применения → requestResync → новый snapshot.
  5. События best effort. Потерю последнего события ловит проверка ревизии каждые 5 с (метаданные в heartbeat/опросе).
  6. Generation-счётчик клиента отсекает ответы и события от предыдущей сессии после reconnect.

11Чат

  • Адресат: текущий канал или личный диалог с user_id (в том числе офлайн).
  • Операции ChatRequest: send, history (курсор, вперёд/назад), dialogs, read-позиция. Текст ≤ 1000 B UTF-8, страница ≤ 1200 B.
  • Сервер: очередь 128, ≤ 4 ожидающих на пользователя, таймаут 3 с. Права проверяются под policyGate, SQLite — вне голосового цикла.
  • Ошибки: клиенту показываются только отказы domain.ChatRejection (проверка текста, адресата, прав); сбои SQLite приходят как «хранилище чата недоступно; повторите позже», подробности — в лог (chatErrorText).   • Идемпотентность: уникальная пара (sender_id, client_id) — повтор после reconnect не создаёт дубль.
  • ChatChanged — уведомление «есть новое»; клиент дополнительно опрашивает раз в 5 с для восстановления потерь.

Linux ограничивает запрос значением net.core.rmem_max без ошибки: для полного размера нужен предел ≥4194304; Linux дополнительно учитывает socket bookkeeping и возвращает удвоенный SO_RCVBUF. На Linux сервер читает фактический SO_RCVBUF (делит на 2) и логирует effective/clamped при первом сокете и при каждом изменении; на других ОС наблюдение пропускается. Предел поднимает scripts/media-sysctl.sh apply (sysctl.d-файл, больший предел сохраняется, прежнее значение сохраняется для rollback); rmem_default не меняется, уже созданные сокеты сохраняют свой размер. Обёртка не кеширует интерфейсы: каждый запрос Interfaces/InterfaceByIndex/InterfaceByName строит свой снимок stdnet, поэтому новые ICE agents видят текущие интерфейсы, а параллельные PeerConnection не обновляют общий кеш. Это ёмкость для burst/keyframe, а не целевая задержка. Буфер каждого ICE socket дополняет бюджет памяти; сокеты создаются по интерфейсам/PeerConnection. Источники: internal/media/network.go, webrtc.go, manager.go; Linux socket(7).
  • Одна очередь удерживает до 2048 входных буферов Pion receiveMTU 1500: около 2,93 MiB плюс packet/header metadata/slices; writer дополнительно удерживает один кадр, publisher — один собираемый кадр и окно перестановки до 2048 пакетов. Для S publisher и V зрителей консервативный бюджет входных backing buffers: 2,93 × (2S + 2V) MiB без учёта совместного владения. NACK cache зрителя дополнительно хранит до 2048 копий RTP, observer — 2048 sequence slots. Пулы Pion могут удерживать выделенную память после остановки. Полный бюджет включает metadata, DTLS/SRTP/ICE и ресурсы Pion. Общий hard limit числа media-подписок не введён; ёмкость VPS требует измерений.

Client cleanup останавливает capture при ошибке создания PC, учитывает cancellation до первого await, закрывает PC при ошибке receiver setup и явно снимает disconnect timer/listener. Снимок под publisher mutex, Pion getters и логирование после освобождения. Observer внутри NACK responder считает RTX и повторную sequence number в окне 2048; суммы не включают SRTP/UDP/IP overhead. Клиент показывает выбранные и фактические размер/FPS/codec, доступный encoder/decoder implementation и qualityLimitationReason; окно зрителя обновляет размер кадра по событиям loadedmetadata и resize элемента video, поэтому уменьшенные первые кадры (пока sender разгоняет битрейт) не остаются в заголовке. Источники: internal/media/metrics.go, transport_metrics.go, screenStats.ts, ConnectionStatsPopup.tsx, ScreenViews.tsx.

Раз в секунду reconcile worker обновляет оценку скорости каждого подключённого зрителя, уже получившего кадр. Оценка появляется только при сетевом сигнале: потеря >10% или свежий (не старше 5 с) REMB от самого зрителя. Оценка без сигнала ограничения (потеря ≥2% или свежий REMB) дольше 30 с (rateReleaseAfter) снимается: зритель снова без ограничения и без pacing. Потеря считается не по fraction lost одного отчёта, а по разнице накопленных счётчиков RTCP Receiver Report (extended highest sequence number, cumulative lost как знаковое 24-битное) для primary SSRC зрителя: измерение требует ≥100 пакетов, окно, не набравшее их за 5 с, начинается заново, каждый отчёт учитывается один раз; до этого зритель не ограничивает источник и не pacing-уется. При потере >10% оценка = min(оценка, фактически отправлено за секунду, включая RTX) × 0,85; при потере <2% растёт не более чем на 8%/с и не выше 1,5× фактически отправленного (простаивающий экран не раздувает оценку); между порогами или без нового измерения держится, а растёт только при отсутствии измерения или потере <2%; свежий REMB зрителя — верхняя граница; pacing не делает кадр устаревшим сам по себе: если оставшиеся байты кадра не успевают за 80% времени до истечения его бюджета, остаток идёт со скоростью, которая успевает, или сразу, если время вышло (framePaceRate); минимум 300 кбит/с. Очереди сервера (переполнение, устаревание) не снижают оценку: это обычно CPU/socket сервера, а pacing сам может делать кадры устаревшими; они видны как congestion_events. Потолок источника = 0,9 × наименьшая оценка среди зрителей не ниже max(300 кбит/с, 25% медианы); медиана считается по всем активным зрителям (подключён и уже получил кадр), зритель без оценки считается неограниченным (100 Мбит/с), поэтому меньшинство зрителей с потерями не становится медианой; если все оценки ниже порога, потолка нет; более медленные помечаются slow и не снижают качество остальным. Publisher получает REMB с этим потолком каждую секунду (100 Мбит/с, если оценок нет); libwebrtc применяет REMB как верхний предел target bitrate и при согласованном transport-cc, goog-remb объявлен для всех кодеков. Клиент не меняется: maxBitrate пользователя остаётся потолком encoder. Writer зрителя отправляет primary RTP со скоростью 2,5 × оценка − измеренный RTX за секунду (как pacing factor libwebrtc), первые 20 мс данных — без ожидания; ожидание без блокировок, с проверкой возраста кадра перед каждым пакетом, поэтому второй очереди нет и устаревшие кадры сбрасываются прежними лимитами. Transport-wide sequence numbers не переносятся между соединениями. Повторы Pion NACK responder не ограничены по возрасту (только кешем 2048 пакетов). Метрики: source_ceiling_kbps, estimate_kbps, rtx_kbps, rr_loss_percent (последнее измерение по счётчикам RR), viewer_remb_kbps, slow, congestion_events в строке screen metrics. Источники: internal/media/adaptive.go, recovery.go, subscriber.go, frames.go, manager.go, codecs.go, cmd/server/main.go, scripts/redeploy-server.sh, deploy-server.ps1.

14Что протокол не делает

  • Не E2E: сервер расшифровывает и видит голос и control.
  • Не скрывает: IP/порты, размеры и тайминг пакетов, KeyOwnerID и Counter, имя/ключи/версию в handshake.
  • Нет rekey внутри долгой сессии — новые ключи только при новом handshake.
  • Нет защиты первого TOFU-контакта от активного MITM и нет процедуры ротации ключа сервера.
  • Нет adaptive jitter и Opus FEC/DTX; потери компенсируют VoiceBundle (если включён) и PLC — см. раздел 08.
  • Собственная криптосхема (не TLS/Noise), внешнего аудита и fuzz-тестов wire format нет.
  • Открытая регистрация: любой новый ключ создаёт аккаунт.
